## 1. 目的と前提

| 項目 | 内容 |
|---|---|
| アプリ名 | **そぞろつづり**（正式名称：そぞろつづり ― 小さな旅の記録帳）。ひらがなで表記し、リポジトリ名やURLには `sozorotsuzuri` を使う |
| 名前の由来 | 「そぞろ（気の向くままに）」＋「つづり（書き綴ったもの）」。気の向くままに歩いた旅を、そっと綴っておく帳面 |
| 目的 | 旅行の計画・移動・記録・費用・発信を、スマホ1台で完結させる |
| 利用者 | 本人のみ（1名） |
| 利用場面 | 主に外出先・旅行中のスマホ。計画はPCでも行う |
| 開発方針 | **段階的に作る。** Phase 1 は GAS を中心に素早く形にする。本格的にサーバーへ置いて公開する必要が出たら Phase 2 で作り直す |
| 移行への備え | データ構造と画面⇔サーバー間のやり取り（API）を GAS に依存しない形で設計し、作り直しのコストを下げる |
| 対象地域 | 拠点は千葉。対象は **千葉・茨城・東京・埼玉・神奈川**。交通データは **千葉から試し**、順に広げる（5.4） |
| 電波がない場所 | **使えるようにする。** ただし機能は絞ってよい（4.1） |
| 納期 | 設けない。優先度の高いものから順に作る |

## 2. 用語

| 用語 | 意味 |
|---|---|
| 旅行（プロジェクト） | 期間・行き先を持つ旅行の単位。ほかのデータはすべてどれかの旅行に属する |
| 予定 | 日時と場所を持つ計画（例：10:00 清水寺） |
| 記録（ログ） | 旅行中に投稿する短い記録。写真・文章・位置・日時・タグを持つ |
| 支出 | お金を使った記録。交通費とそれ以外（食事・購入品など）を区別する |

| 旅行記 | 記録をまとめた、ブログ記事風のまとめ |
| ハイライト画像 | 旅行の要点を1枚にまとめた、SNS投稿用の画像 |
| 未送信データ | 電波がないときに端末に保存し、まだサーバーに送っていないデータ |
| 同期 | 端末のデータとサーバーのデータを揃えること |

## 4. 非機能要件

| 項目 | 内容（案） |
|---|---|
| 利用者・認証 | 本人のみ。方式は未定（5.2、8.） |
| 対応端末 | 本人は **Android（Chrome）**。将来ほかの人も使えるよう、iPhone（Safari）でも動く作りにする（4.2）。ホーム画面に追加してアプリのように使う。PCでも使える |
| 電波がない場所 | 4.1 のとおり |
| データ保存先 | サーバー：スプレッドシート（文字データ）とGoogleドライブ（写真）。端末：ブラウザ内のデータベース（IndexedDB） |
| 写真 | 端末で長辺1600px程度・数百KBに縮小してから保存・送信する。元の写真はスマホのアルバムに残る |
| 費用 | Phase 1 は無料の範囲。有料APIは必要になったら検討する |
| 速度 | 操作はまず端末に保存して画面に反映し、サーバーへの送信は裏で行う。GASの応答（1〜3秒）を待たせない |
| バックアップ | サーバー側はスプレッドシートとドライブなので、自分で書き出せる |
| データの移しやすさ | 全データをJSON/CSVで書き出せるようにし、Phase 2 へ移せるようにする |

### 4.1 電波がない場所での動き

**方針：** アプリは常に端末に保存されたデータで動き、電波があるときにサーバーと同期する。

| 場面 | 動き |
|---|---|
| アプリを開く | 一度開いたことがあれば、電波がなくても開ける |
| 見る | 旅行・日程・持ち物・費用・メモ・記録の一覧は、端末に保存されたものを表示する |
| 入力・編集 | 端末に保存し、「未送信」として印をつける。画面には「未送信 3件」のように件数を出す |
| 写真付きの投稿 | 写真は送信が済むまで端末に保存しておく。電波が戻ったら自動で送る。手動で「再送信」もできる |
| 電波が戻ったとき | 未送信データを古い順に送る。送れたものから印を外す。失敗したものは次の機会にもう一度送る |
| 電波が必要なもの | 自治体タグの自動付与、地図、外部アプリでの経路検索、時刻表データの更新。電波が戻ってから行う |
| 同じデータを2台で編集したとき | スマホとPCの両方で同じものを編集した場合は、後から保存したほうを残す（使うのは本人1人なので、これで十分と判断） |

**注意点**
- iPhone（Safari）では、ホーム画面に追加しないで使うと、しばらく開かなかったときに端末のデータが消されることがある。そのため、**ホーム画面に追加して使う前提**にする。あわせて、データを消されにくくする設定（persistent storage）も申請する。
- 未送信の写真が端末にある間は、アプリのデータを削除しないよう画面で知らせる。

### 4.2 iPhone でも動かすための約束事

本人は Android だが、あとから iPhone に対応しようとして作り直しにならないよう、**最初から両方で動く機能だけを使う。**

| 機能 | Android（Chrome） | iPhone（Safari） | 方針 |
|---|---|---|---|
| ホーム画面に追加・電波なしで開く | ○ | ○ | 使う |
| 端末への保存（IndexedDB） | ○ | ○（ホーム画面に追加すれば、7日で消える制限の対象外） | 使う。サーバーを正本にし、端末は「控え＋未送信」と考える |
| 現在地（GPS） | ○ | ○ | 使う |
| カメラ・写真の選択 | ○ | ○ | 使う |
| 画像の共有（Xへ送る等） | ○ | ○ | 使う（ハイライト画像の共有に） |
| 裏での自動送信（Background Sync） | ○ | × | **使わない。** アプリを開いたとき・画面に戻ったとき・電波が戻ったときに送る |
| プッシュ通知 | ○ | △（ホーム画面に追加した場合のみ） | 当面使わない |

**結論：** この約束事を守れば、iPhone 対応が致命的な問題になる可能性は低い。どうしてもWebアプリでは無理なことが出てきた場合も、同じ画面のコードを包んでスマホアプリにする方法（Capacitor など）がある。

**ほかの人にも使ってもらう場合に別途必要になること（Phase 2 で対応）**
- 一人ずつのログインと、データを人ごとに分けること（合言葉方式では足りない）
- 利用規約・プライバシーポリシーの用意
- ODPT のデータを表示するなら、「データの正確さは保証されない」旨と問い合わせ先の表示（5.5）

準備として、すべてのデータに `ownerId`（持ち主）の項目を最初から入れておく。今は本人の値だけが入る。

## 5. 実現方式

### 5.1 Phase 1 の構成（v0.3 で変更）

**変更の理由：** GAS が作る画面（HtmlService）は、電波がないと開けない。また、外側の枠の中で表示されるため、位置情報が使えない可能性が高い。「電波がなくても使える」を満たすには、画面をGASから切り離す必要がある。

```
 スマホ（ホーム画面に追加したWebアプリ = PWA）
 ┌───────────────────────────────┐
 │ 画面（HTML/JavaScript）        │  ← GitHub Pages に置く（無料）
 │ 端末内の保存（IndexedDB）      │  ← 電波がないときもここで動く
 │ 未送信データの送信待ち        │
 └───────────┬───────────────────┘
             │ 電波があるときに同期（HTTPS）
 ┌───────────▼───────────────────┐
 │ GAS（API として動かす）         │
 │  ・データの保存/取得            │ → スプレッドシート
 │  ・写真の保存                   │ → Googleドライブ
 │  ・住所から自治体名を調べる     │ → GASのMapsサービス
 │  ・時刻表データの定期更新       │ → 時間指定の自動実行で GTFS を取得し、
 │                                 │   軽いJSONに変換してドライブに保存
 └───────────────────────────────┘
```

| 担当 | 役割 |
|---|---|
| PWA（画面） | 表示・入力、GPS、カメラ、端末への保存、同期、ハイライト画像の作成 |
| GAS（API） | データの保存、写真の保存、自治体名の検索、時刻表データの定期更新 |

- 試作済みの画面（v0.1）は、ほぼそのまま PWA に移せる。サーバーを呼ぶ部分だけを書き換える。
- Phase 2 でサーバーを作り直すときも、GASの部分を置き換えるだけで済む。

### 5.2 認証（誰が使えるか）

PWA から GAS を呼ぶ場合、GAS の「自分のGoogleアカウントでログインしたときだけ使える」設定はそのままでは使えない（別のサイトからの呼び出しになるため）。次のどちらかにする。

| 方式 | しくみ | 長所 | 短所 |
|---|---|---|---|
| **A. 合言葉（APIキー）** | GASは誰でも呼べる設定にし、長くランダムな合言葉を知っている人だけ処理する | 作るのが簡単。電波がないときの扱いも単純 | 合言葉が漏れると使われてしまう（いつでも変更できる） |
| **B. Googleでログイン** | PWAでGoogleログインし、GAS側で本人のアカウントか確かめる | 安全性が高い | Google Cloud での設定が必要。ログインの有効期限（1時間）の扱いが少し複雑 |

> **決定：A（合言葉）で始める。** 必要になったら B に切り替える。
>
> 注意：PWA の画面は GitHub Pages で誰でも見られる場所に置くため、**合言葉や ODPT のアクセストークンを画面のコードに書かない。** 合言葉は初回に端末で入力して保存する。ODPT のトークンは GAS のスクリプト プロパティにだけ置く。

### 5.3 交通データ

**決定事項**
- 経路検索・所要時間・運賃は、**外部アプリ（Googleマップ・乗換案内など）で調べ、結果をこのアプリに記録する**。
- 時刻表などのデータは、リアルタイムで取らず、**定期的に更新する**（月1回〜毎日。頻度は運用しながら決める）。

**データの取得元**

| 取得元 | 種類 | 使いみち | 状況 |
|---|---|---|---|
| **外部アプリと連携** | 無料 | 経路・所要時間・運賃を調べる | v0.4 で対応 |
| **GTFS-JP**（GTFSデータリポジトリ） | 無料・登録不要 | バスの時刻表、「次の便」 | 5.4 のとおりバスのみ。定期更新で取り込む |
| **ODPT**（公共交通オープンデータセンター） | 無料・開発者登録が必要 | 鉄道・飛行機の時刻表 | 首都圏の鉄道のデータがどこまであるか、登録して確認が必要 |
| **駅すぱあと API** | 有料（フリープランあり） | 鉄道の経路・運賃をアプリの中で出したくなったとき | 将来の検討 |
| **NAVITIME API** | 有料 | 同上 | 将来の検討 |
| **Google Maps Routes API** | 従量課金（無料枠あり） | 同上 | 日本の電車の結果が出るか未確認 |

**定期更新のしくみ**
1. GAS の時間指定の自動実行で、対象のGTFSデータ（zip）を取得する
2. アプリで使う形（停留所・便・時刻）の軽いJSONに変換し、ドライブに保存する
3. 旅行の前に、その旅行で使う路線のデータを端末に取り込む（電波がなくても「次の便」が出せる）

### 5.4 対象地域の交通データ状況（2026-11-27 調査）

GTFSデータリポジトリのAPI（`api.gtfs-data.jp/v2/files?pref=N`）で、県ごとに公開されているデータを数えた結果：

| 県 | 公開データ数 | 内容 |
|---|---|---|
| 千葉 | 10 | すべてバス（主にコミュニティバス）。印西市、香取市、京成バス千葉ウエスト（塩浜営業所）、君津市×2、松戸市×2、流山市、成田市、四街道市 |
| 東京 | 10 | バス、デマンド交通、神津島村営バス、小笠原村営バス |
| 埼玉 | 19 | バス、ワゴンバス、乗合タクシー |
| 神奈川 | 7 | バス |
| 茨城 | 8 | バス |

- **鉄道とフェリーのデータは、5県ともこのリポジトリには見当たらない。** バスも路線網の一部だけ（大手の路線バスはほとんど入っていない）。
- ダウンロードにAPIキーは不要。ライセンスは CC BY 4.0 または CC0（出典の表示が必要なものがある）。停留所と路線の地図用データ（GeoJSON）も付いている。

**対象地域についての方針**
- 記録・タグ・費用：最初から5県すべてを対象にする（自治体名は住所から調べるので、データ量の問題がない）
- バスの「次の便」：千葉のデータで試し、使えれば他の県へ広げる
- 鉄道：当面は外部アプリと連携して対応する。ODPTのデータを確認してから、時刻表を取り込むか決める

### 5.5 ODPT（公共交通オープンデータセンター）の詳細（2026-11-27 調査）

**個人でも使えるか**
- ユーザ登録は無料。メールで申請し、最大2営業日ほどで承認される。
- 規約に個人を除外する記述はない（法人やグループの場合の決まりが別にあり、個人での登録も前提にしている書き方）。アカウント情報として氏名・所属・連絡先などを登録する。
- **アプリを公開する義務はない。** 基本ライセンスは「成果物を一般に公開できる」と許可する書き方で、公開を求めてはいない。営利・非営利も問わない。

**守る必要があること（基本ライセンス）**
- データを、他人が再利用できる形で公開・再配布しない → 取得したデータは GAS・ドライブ・端末の中だけで使い、GitHub に置かない
- データが更新されたら、アプリの表示もすぐ更新する → 定期更新のしくみ（5.3）で対応
- アクセストークンを他人に知られないようにする → GAS 側にだけ置く（5.2）
- 他人に使ってもらう場合は、「データの正確さは保証されない」旨と、問い合わせ先をアプリに表示する

**このアプリでの使い方（案）**
- 本人の移動の中心である千葉の鉄道が含まれないため、**鉄道は当面、外部アプリとの連携で対応する**方針は変えない。
- 登録しておけば、東京メトロ・つくばエクスプレスの時刻表を「次の便」に使える。急ぎではない。
- 参考：チャレンジ限定のデータ（JR東日本など）は、このアプリを公共交通オープンデータチャレンジ2026に応募すれば、開催期間中は使える。応募してみるのも一つの楽しみ方。

## 6. データ構造（案）

```
旅行 Trip ─┬─ 予定 Schedule   （日時・場所・移動手段・出発/到着）
           ├─ 記録 Log        （写真・文章・日時・緯度経度・タグ）
           ├─ 支出 Expense    （金額・通貨・カテゴリ・交通費かどうか・記録/予定との紐づけ）
           ├─ 持ち物 Packing
           ├─ メモ Note
           └─ 旅行記 Story    （本文・使う記録・ハイライト画像）
タグ Tag（自治体 / スポット）── 記録・支出・予定に複数付けられる
時刻表 Timetable（GTFSから変換したデータ。旅行とは別に管理）
```

**同期のための共通項目：** すべてのデータに次の項目を持たせる。
- `id`：端末で作るランダムなID。電波がなくても重複しないようにするため
- `updatedAt`：最終更新日時
- `deleted`：削除の印。削除も同期できるようにするため
- `ownerId`：データの持ち主。今は本人のみ。将来ほかの人が使うときの準備（4.2）
